## Maintenance identity and process isolation

The API, notification queue worker and ordinary scheduler retain only the web runtime credential. They must not receive migration/maintenance credentials, access another service's environment/PID namespace, share resolved configuration caches, mount a maintenance secret, or access a Docker/control-plane socket. No privileged maintenance consumer reads the ordinary database queue: runtime SQL can write that queue. Cleanup job classes fail closed on an ordinary worker.

A separately authorized private service uses the same immutable image with `msprout-entrypoint maintenance`. It runs only fixed commands (`operations:maintenance prune` at 02:15 and `operations:maintenance purge-revoked` at 02:45), never Apache or `queue:work`. Single-operation invocation is `msprout-entrypoint maintenance prune` or `msprout-entrypoint maintenance purge-revoked`. Keep one scheduler replica; changes to replicas/cadence need operational review. Override the API HTTP healthcheck for this non-HTTP service and verify process/schedule-failure monitoring in the target; an API liveness endpoint is not its health proof. Church gates also serialize overlapping transactions. Notifications, push and email remain ordinary-worker work.

Nonsecret `DB_MAINTENANCE_USERNAME` identifies the independent role in migration/application configuration. Only the maintenance service sets `DB_USERNAME` to this role; `DB_RUNTIME_USERNAME` retains the web role name. Mount its independent password read-only at `/run/secrets/msprout-maintenance-password`. Incoming `DB_PASSWORD`, database URLs and migration credentials must be absent. Startup reads the private file into this process only, selects a private file cache (preserving scheduler overlap locks), array session and null queue, then creates its own ephemeral config cache. Ordinary startup rejects a mounted maintenance secret, maintenance identity/process setting or migration credentials. Privileged HTTP is rejected before controllers. Flags/GUCs never confer SQL authority: authenticated session and current role must both match the maintenance identity.

Provision the LOGIN principal only through a separately approved target operation: NOSUPERUSER/NOBYPASSRLS/NOCREATEDB/NOCREATEROLE/NOINHERIT/NOREPLICATION, no memberships in either direction, no database/table/function ownership, distinct from runtime/platform/migration. The additive migration never creates a production role/password. With no maintenance role configured it still revokes dangerous grants and leaves cleanup unavailable. An invalid role aborts the migration transaction; never substitute runtime/owner credentials. Review historical grants before target execution.

Minimum grants are schema USAGE and five current fixed-search-path helpers; the two preserved legacy signatures remain owner-only. Worker table grants are SELECT on churches/Users/applications/sessions/password-reset tokens, UPDATE(id) for church/User row locks, narrow application redaction-column UPDATE, eligible-identity/session/token DELETE and append-only audit INSERT. No queue, membership/attendance/feed/receipt writes, audit mutation, ownership or RLS bypass. Function owners remain the reviewed migration owner, not either application principal; search_path remains pg_catalog with qualified tables.

Cleanup SQL, sorted User locks, model changes and canonical audits use the maintenance process's one default authenticated connection. No production connection switch or independent audit commit exists. Each church owns its C coordination transaction; a later failure rolls back that church and suppresses the final success summary while retaining earlier committed churches. Global retention and its required audit share their own transaction. Conservative feed/receipt rules remain intact.

Before deployment verify service secret scope, private mount, PID/environment/config-cache isolation, all role/ACL/owner/RLS attributes, actual SCRAM authentication, runtime SET ROLE denial, missing/invalid-secret refusal, ordinary HTTP availability and maintenance HTTP refusal. Apply both additive BDE migrations in a separately approved stop/drain window that also closes ordinary runtime login/admission and drains existing runtime SQL sessions; never expose construction without the isolation migration. Keep the reviewed operator/migration path available. Inventory previously queued cleanup jobs without exposing payloads; never feed shared queue rows to the privileged service, delete them automatically or reinterpret them as maintenance authority. Old workers must not continue cleanup with revoked credentials. Verify schedules and sanitized failures after startup. Never roll back by regranting runtime EXECUTE. Target infrastructure/credential distribution is NOT TESTED locally and remains a mandatory deployment prerequisite.

The disposable separate-container proof (`node scripts/compatibility/integration/process-isolation.mjs`) exercised the real entrypoint, independent authentication, ordinary SQL/SET ROLE/catalog denials, and missing/misplaced-secret refusal. ## Admission seal and old-writer drainage

These are manual, separately authorized operational steps, not normal application bootstrap.

1. From the verified control connection, commit `ALTER DATABASE <exact_target> ALLOW_CONNECTIONS false` and `ALTER ROLE <exact_runtime> NOLOGIN`. Identifiers must come from the reviewed target receipt; never paste a user-provided identifier. Preserve the existing owner target connection. Once sealed, no new target-database session—including an old pool reconnect—may enter.
2. In the retained owner target connection, run `SELECT public.record_publication_admission_seal();`. It requires a previously committed database seal, a NOLOGIN SCRAM runtime and inactive/uninitialized publication. It records private comparison evidence; runtime cannot read it or invoke this function. Do not export that evidence.
3. Rotate the existing runtime credential through the approved private channel to a new independently generated secret while admission remains sealed. Give it only to the reviewed new deployment. Keep APP_KEY and User passwords unchanged. No literal credential command, raw parameter log or archived environment file is permitted. If safe distribution/authentication qualification is unavailable, remain sealed and escalate.
4. Close all old database sessions cleanly after their transactions finish. The function refuses *every* other target-database backend and every prepared transaction, including idle sessions and cached-sequence consumers. A lock acquired only by new code is not drainage. If cancellation/termination or prepared-transaction resolution is genuinely necessary, obtain explicit target-specific authorization; never blindly terminate backends or roll back unknown prepared work.
5. Verify `CACHE 1` on the existing global sequence after old consumers drain. If the sequence used a larger cache, changing its catalog setting alone does not prove old cached consumers exited. Preserve the current allocation floor; never call setval, RESTART or arbitrarily reseed it. Unknown historical pruning and served device cursors are not committed/applied evidence.
6. Keep the role NOLOGIN and target admission sealed. Collect sanitized process/session/prepared-transaction and authentication evidence with the correlation UUID. A previously active runtime with an old secret must not be able to reenter through any relevant authentication path after reopening. The isolated fixture proves this using actual SCRAM authentication and old-credential refusal; production must prove its own ingress and deployment state.

## Atomic cutover — only after future recovery and operational approval

In the retained owner target connection, begin a transaction and call:

```sql
SELECT public.activate_coordinated_publication('<approved-correlation-uuid>'::uuid);
```

The function requires the trusted relation owner with qualified administrative/RLS-bypass authority, the committed admission seal, a changed SCRAM verifier, restricted dedicated runtime, no extra direct writer rights, no other target backend/prepared transaction, CACHE1 and no preexisting initialized/mixed publication state. It fails closed; it does not terminate sessions, repair identity collisions, modify HBA, rotate credentials or override unsafe prerequisites.

For each existing church in UUID order it records retained committed MAX(sequence) or0 as feed_head and the existing global allocated value as the conservative floor, with a fresh epoch. The floor may include rolled-back or reserved allocations; it does **not** claim committed attendance or historical retention. Existing pruned_through remains NULL/unknown. Device recovery flags are set without copying served cursors into applied evidence or fabricating receipt coverage.

In the same transaction it withdraws runtime direct feed INSERT, sequence access and progress-head update rights; grants only the narrow supported append function; marks publication active; and writes required canonical `sync.publication.activated` audit evidence with the supplied correlation UUID. If any statement or audit fails, metadata, flags and privilege changes roll back together. No fallback publisher runs. Inspect sanitized results/rights and commit only after all required checks pass; otherwise roll back and follow the abort section.

Verify the resulting epoch/head/floor, private control ownership, narrow function grants, forced tenant RLS, restricted role, original grants withdrawn, canonical audit, no artificial applied/receipt credit, and no sequence reset. Preserve this receipt separately from application source. Do not resume traffic merely because this SQL call returned.

## Maintenance and partial success

New jobs use purpose-specific C system authority, ordered church enumeration and one transaction per church. Each church's deletion/coverage flags and required canonical church audit commit together. A later church failure propagates, preserves earlier successful church commits, and produces no false all-church success summary. Retry reevaluates remaining work safely. Global operational/security cleanup and eligible application/User cleanup have their own audited transactions; User locks precede application locks, and hidden memberships prevent unsafe identity deletion.

Thirty-day operational/secret and180-day security/receipt/authorization minima and exact inclusive boundaries remain unchanged; feed minimum remains90days. No canonical audit_events deletion is introduced. Actual receipt deletion marks only matching devices as pruned/recovery-required. An unknown prior pruning watermark stays unknown. While reconstruction is unavailable, any retained device cursor or authorization holds its church's feed; served progress, lease expiry and successful cleanup never mean recovery complete. Do not erase this hold to reduce storage without separately approved recovery/retention work.

## Abort and recovery

- **Before activation commit:** keep admission sealed and runtime NOLOGIN. A failed activation transaction leaves the old grants/metadata state intact, but prior credential rotation is a separate committed security action. Do not restore an old credential. Investigate the precise failure; a legacy restart would need reviewed old-compatible code configured with the new secret and separate authorization to reopen.
- **After activation commit:** keep traffic stopped on a failed check. Do not silently regrant direct feed/sequence/head rights, deactivate metadata, reset the sequence, change epochs or roll back to an unqualified old producer. Preserve the commit, database state, canonical audit and sanitized evidence; obtain a separately reviewed forward-repair/abort plan. Remaining snapshots and client reconstruction are not an emergency bypass.
- **Unknown old transaction, privilege, HBA path, normalized identity collision or lost operator connection:** fail closed and escalate. No cleanup, forced drainage, protected migration or metadata repair is implied by this runbook.
- **Existing client work:** preserve all profile identities, keys, encrypted rows, drafts, conflicts, event IDs and pending outbox. A recovery-required response is not an acknowledgment, lease replacement, authorization denial or permission to discard local intent.

Current BDE qualification exercises these controls only in a separately guarded disposable PostgreSQL18 environment. It is not production drainage, deployment, protected-data migration or active recovery qualification.
