## Root cause and fix

Fresh-request regression reproduced successful password login, successful TOTP HTTP 204 and immediate `/platform/me` HTTP 500 with both database payload-encryption settings. A test-only exception mapper captured only `Illuminate\Database\QueryException` and SQLSTATE `22P02`; SQL, bindings, session identifiers and payloads were never emitted.

`auth:platform` correctly restores a `PlatformAdmin` using its UUID from the platform guard key, then selects `platform` as Laravel's default guard. `show()` passes activation/MFA checks and constructs the expected JSON. During the outer `StartSession` response unwind, Laravel's default `DatabaseSessionHandler::userId()` resolves that selected guard and attempts to update `sessions.user_id` with the platform UUID. The existing column is a nullable integer for church users. PostgreSQL rejects the UUID, and the privacy-preserving exception handler converts the exception into the generic correlated 500. Challenge routes have no `auth:platform` middleware and their fresh-request default guard remains `web`, explaining the earlier 204.

Resolved middleware order was inspected read-only: platform cookie selection → cookie decryption → queued cookies → session start → shared errors → platform CSRF → platform authentication → bindings → authentication audit. The cookie remains `ministrysprout_platform_session`, scoped to `/platform`. Session rotation, database restoration, provider identifier and controller user type are correct; middleware reordering or relaxed user/MFA checks would not address this failure.

`GuardAwareDatabaseSessionHandler` overrides only metadata user resolution: null for platform requests, explicitly `web` for church requests. `AppServiceProvider` extends the existing database driver with this handler. Laravel retains its standard store construction, optional payload encryption, persistence, expiry and cookie handling. No migration, configuration change, account mutation or API shape change is needed. Church session revocation and rejected-user cleanup continue to query integer metadata. `/platform/me` continues to return exactly `handle` and `online_only`; OpenAPI/client sources remain unchanged and their drift check passed. Production error responses/logging retain existing privacy controls.
