## Evidence and verified mechanism

HUMAN_MANUAL reports successful Music teacher sign-in, then selection/unlock of existing Profile 1, Attendance with a saved Present guest and three pending changes, then Review with two `/session` 401 responses. The tester did not deliberately sign out. Retained Network evidence does **not** establish whether the automatic `POST /logout` occurred in that historical attempt. No human cookies, session rows, credentials or encrypted payloads were accessed for this investigation.

The reported order is reproducible through the current UI in disposable desktop and mobile Chromium contexts. `DeviceProfilesScreen.unlock()` calls `switchProfile()` with `online: navigator.onLine` and `signOut: authRequest('/logout', 'POST')`. When the selected profile is not currently unlocked in memory, `switchProfile()` clears the web session **before** unlocking and marks reauthentication required. A full document navigation or background lock removes the in-memory active key; selecting the same stored Profile 1 afterward still takes this path. Only an already-active same-profile selection is a no-op. The approved [Task 11, Step 5](../superpowers/plans/2026-08-20-ministry-sprout-implementation-roadmap.md) explicitly requires online profile switching to sign out the active server session. This established shared-device safeguard is preserved.

Browser regression proves the frontend sequence `login 200 → session 200 → Use profile 1 → logout 204 → Attendance available → Review session 401`. A subsequent focus activation produces a second session 401 while signed out. These are genuine requests from the application with intercepted endpoints, not live-backend authentication proof. The separate cookie-backed Laravel regression exercises the real Fortify/login/logout/session stack and database session driver in the guarded isolated test database: repeated session reads succeed, logout immediately invalidates the session with the clock frozen, and signing in again restores it. The combined proof establishes automatic profile-selection logout as the cause of the reproduced sequence, not elapsed session age. The historical attempt's uncaptured HTTP trace remains a forensic limitation.

Attendance uses an unlocked encrypted, assignment-scoped, lease-bound local profile. Review uses the authenticated church workspace boundary and never substitutes the offline profile for a server session. Consequently, local Attendance remaining available does not establish online authentication. The 401 and sign-in instruction are correct after logout. The teacher's Review endpoint remains role-scoped; opening it does not grant Owner conflict access.

## Cookie, CSRF, expiry and recovery checks

- Authentication transport uses same-origin cookies, `cache: no-store`, redirect rejection and CSRF initialization plus `X-XSRF-TOKEN` for mutations. Session discovery is a GET and does not require a CSRF token. No bearer token is persisted by the frontend.
- Real cookie-backed test requests reset the Laravel test guard/session-store instances between requests, ensuring authentication comes from the returned cookie. The session cookie is HttpOnly with path `/`; denied session responses remain `no-store, private`.
- Missing CSRF on logout produces **419**, and the existing session remains authenticated. Genuine database-session expiry beyond the configured lifetime produces **401** without logout. Neither distinction relies on a mocked backend.
- Allowlisted local bootstrap configuration reports database sessions, 120-minute lifetime, no expire-on-close, path `/`, domain unset, HttpOnly, SameSite Lax, local HTTP secure flag false, church web/Fortify guard `web`, and loopback frontend stateful hosts. Production secure-cookie enforcement remains intact. These are local configuration facts, not an inspection of the human browser cookie or independent proof of the running server's configuration.
- No throttling alone does not prevent an intentional logout. Backgrounding purges the local encryption key under the separately verified shared-device policy; it does not itself invoke server logout. Reselecting the profile online afterward does. Review activation revalidates the server session and can repeat the denial without causing the initial logout.
- Signing in dispatches workspace-authentication invalidation, **not** an `online` event. Reconnect synchronization listens to `online` and requires an active profile. The isolated recovery test checks encrypted blobs, drafts, outbox, cursors, conflicts and metadata remain byte-for-byte equivalent via a hash; three outbox events remain and zero sync requests occur throughout sign-in/profile selection/Review/re-sign-in. Profile reauthentication metadata is deliberately excluded from the work hash because selection changes it by policy.
