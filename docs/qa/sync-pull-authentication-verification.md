## Confirmed defect and mechanism

`apps/web/index.html` sets `<meta name="referrer" content="no-referrer">`. The authentication transport and general API client already override that policy with `referrerPolicy: 'origin'`; the sync client's push/pull and CSRF fetches did not. Sanctum's `EnsureFrontendRequestsAreStateful` selects its cookie/session middleware only when Referer or Origin matches the configured first-party allowlist. Credentials alone do not cause a headerless API GET to load that session. A browser POST can supply Origin; a same-origin GET under this document policy supplies neither Origin nor Referer.

Isolated Chromium confirms the shipped document's default same-origin GET has neither header, while the corrected client emits only the origin as Referer. Separately, a real cookie-backed Laravel regression freezes time, signs in an isolated Teacher, bootstraps an assigned ministry/device, accepts three events with one record/versions 1–3, then receives the exact pull 401 when Origin/Referer are absent. The same cookies and clock produce pull 200 after adding only an allowed-origin Referer. An untrusted Referer still returns 401; `/auth/session` remains authenticated afterward. No logout is involved. This reproduces the observed failure mechanism and establishes a transport defect without assuming session expiry or profile-switch logout. Historical headers remain the stated forensic limitation.

The approved online **Use profile** logout remains unchanged and was revalidated separately. **Refresh authorization after sign-in** uses the intentional local PIN unlock plus authenticated bootstrap path, without logout. Push acknowledgement is durable before pull: accepted events must not be restored to the outbox merely because download/lease renewal fails. The old zero-pending display counted remaining uploads and could misleadingly imply completion, including after an authorization-read failure forced a synthetic zero count.
