## Implemented behavior

- Separate Conflicts and Temporary guests tabs describe loaded, bounded queues. Owner membership, verified email, actor binding and current-session MFA are checked before protected reads and again before operations. Teacher presentation requests only the restricted needs-review notice; unexpected Owner payloads fail closed.
- Inspect a conflict through its supported detail endpoint. Existing and incoming Present/Absent values, supported actor/device/local/server/correlation provenance and attendance references are distinct. The choice starts unselected, maps to the actual value, and needs a normalized 1–500-character reason.
- Explicit church/case/value/reason confirmation precedes the exact supported `{ choice, reason }` submission. Cancel/Escape returns focus with no write. Synchronous operation guards prevent duplicate actions. Mutation-time detail reads invalidate stale evidence and require a fresh choice; resolved detail reads remove the case without another write.
- Accepted conflict responses require complete matching IDs/status/revision/effective value. Lost, invalid or uncertain outcomes use authoritative detail reads; unavailable reads block further submissions and expose a deliberate Check current outcome action. Validation errors preserve safe inputs only when the current evidence still matches. Changed evidence discovered during validation reconciliation resets the decision.
- Guest actions begin unselected and show one supported form: first/last name and gender for promotion, loaded active student selection for linking, or another loaded pending guest from the same session for merging. No guardian or unsupported fields are requested. Confirmation identifies the source and actual target/consequence; fresh pending and active-student reads protect the write.
- Accepted matching guest responses populate “Confirmed dispositions this visit” and remove repeat actions, including stale pending projections after refresh. The existing guest API returns only up to 100 pending rows, with no resolved-history/detail endpoint. Absence after an uncertain write cannot prove a disposition; the UI states that limitation and blocks repeat actions. No unsupported read, inferred success or complete-history claim is introduced. Resolved canonical merge targets cannot be discovered through this pending-only contract and are not invented.
- Session/role/actor/church/offline invalidation clears protected details/forms/dialogs and suppresses late responses. Verified refresh never resurrects a pending confirmation. Stable workspace headings preserve existing activation coalescing; queue tabs remain mounted behind details so Back preserves the selected tab and focus. Successful removal returns focus to the queue heading.
- Shared navy/blue/emerald primitives, native accessible dialogs, reason feedback, 44-pixel choices, responsive comparisons/provenance wrapping and enlarged text support desktop/tablet/phone use. Reports/history link to the existing route; no UI-12 report redesign is implemented.

No production backend, API/generated contract, schema, permission, dependency, scanner/CI policy, encryption/key/lease, attendance repository, outbox or sync behavior changed. Original attendance, append-only revisions and correlated audit evidence remain enforced by existing transactional server operations. No human profile, ministry, account or attendance data was operated.
