A 204 initializes CSRF; it does not establish authentication. The continuation button is rendered unconditionally and is not proof of a session. The agent did not inspect live cookies, request bodies or the current identity.

Fortify attaches `guest:web` to POST `/login`. Laravel's `RedirectIfAuthenticated` returns its default `/` redirect before the login controller when the web guard is already authenticated, even with JSON Accept/XHR headers. It never validates the newly submitted email/password on that branch. Vite preserves the incoming Host (`changeOrigin: false`), explaining the absolute frontend-origin Location. This differs from successful fresh Fortify login: with `Accept: application/json` it returns 200 / `two_factor: false`; non-JSON successful login defaults to `/account/verify-email`, not `/` (unless an intended URL exists). The shipped auth transport already sends JSON Accept and XHR headers.

The transport's deliberate `redirect: 'error'` makes Chromium reject a 302 as a fetch TypeError. The old catch-all message interpreted such unclassified errors as offline. No throttling does not eliminate HTTP redirects, and this exception is not evidence of lost connectivity or failed credentials. The observed sequence matches the existing-session branch; historical cookie/identity state remains unverified.
