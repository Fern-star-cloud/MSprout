Run commands from this repository root and database suites sequentially. The runner refuses another working directory before Git, Docker or bootstrap. `prepare` creates independent labelled containers, internal network, volume, PostgreSQL18 cluster, setup/runtime identities, database, credentials and APP_KEY. It compares system identity and mounts with the protected development container, exposes no database port, and copies only tracked/new public API source. It reads a retained dependency archive without changing the previous environment. No private environment, SQLite, browser profile or old test database is mounted or used. No automatic cleanup is performed.

`bootstrap.php` checks the explicit marker, target names, loopback, absent connection strings, empty-or-absent generated dotenv fixture and independent system identity before the repository bootstrap can create a test database or rotate a runtime role. Workers run that guard in probe mode and inherit the initialized restricted role; they cannot rotate credentials. Compatibility aliases satisfy the unchanged P2-1A worker's existing initialized-role assertions. The historical P2-1A runner, checkpoint pin, worker and tests remain unchanged.

Tests are explicitly invoked from `tests/Compatibility`, outside ordinary suite discovery. The ordinary API suite runs separately through the same new guard. Evidence is ignored under `.git/msprout-compat-b4-p2-1b-a-20261017/`: sanitized isolation/guard receipts, every attempt and paired input hashes, scanner results and preservation observations. No credentials are written to those receipts.

New fixture setup re-probes independent identity and verifies both Laravel connection configurations before refresh, seeding, test grants or cleanup. A substituted foreign database configuration is refused without making that connection. Do not invoke these tests through an unguarded repository bootstrap; ordinary API bootstrap has its own separate-test-database policy and is not this task's independent-environment authorization.

`PublisherScenario::initialize` seeds hypothetical qualified metadata only in this disposable database. It is not a drain/bootstrap algorithm or original-event evidence. `grantForProof` checks the initialized disposable runtime name before issuing a temporary test-only SQL EXECUTE grant; teardown revokes it. The migration grants neither PUBLIC nor ordinary runtime execution. No application caller uses the new publisher, and legacy INSERT/sequence/head-update rights remain unchanged. The passing proof cannot establish a production committed-head invariant while those old paths remain available.

The PHP contract requires a trusted TenantContext/Laravel-owned outer transaction at level1, READ COMMITTED isolation, and primary gate acquisition before domain/advisory locks. The context is usable only during its issuing callback and checks object registration, PDO identity/live transaction, church, PostgreSQL backend and transaction identity. New primary acquisition inside a savepoint is rejected. Reuse the issuing coordinator for nested work after domain locks; do not reacquire a new primary coordinator late. Do not manually create transaction/savepoint state outside Laravel's ownership accounting or catch a failed domain operation and continue its owning transaction. The helper introduces no retry or independent commit.

The SQL routine independently locks the church before progress and sequence allocation. It checks tenant scope, expected transaction, matching qualified epoch, supported fields/actions, composite tenant FKs and CACHE1, then appends and advances head atomically. Its transaction-id argument is an identity consistency check, not an authentication secret. SQL execution permission is the database capability; this routine does not prove HTTP/session liveness or prove that an arbitrary privileged SQL caller acquired its earlier domain locks correctly. Future activation must qualify those authority and ordering boundaries and remove bypass grants after verified old-writer drainage.

The new worker uses IPC barriers, bounded `stream_select`, a test-only statement deadline and database-observed blocking relationships. Timeout/deadlock errors are exposed, followed by separate whole-operation retries. The cache witness uses a new standalone sequence and independent backend caches; the publisher refusal changes only CACHE configuration on the disposable feed sequence and restores it, without `setval` or RESTART. Ordinary fixture table refresh remains confined to the disposable environment.

Fresh post-gate reads reject changed church/member/role/email/MFA state, but do not fence subsequent global account writes or establish that a request's loaded session still exists. The same-User/two-church and deleted-session tests deliberately preserve those limitation witnesses. P2-1B-C must qualify session/recent-authentication/account authority, signed invitations and trusted maintenance before affected activation. No global Fortify change is made here.
